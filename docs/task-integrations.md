# タスク結果を他のツールで使う

AIに画面で確認した値や作業結果を返すよう依頼すると、履歴の［実行結果］やMCPで同じ結果を確認できます。Webhookを設定すると、タスクの終了時に指定先へ送信します。

たとえば「注文管理画面で発送待ちを確認し、件数と注文番号の一覧を返して。注文は変更しないでください」と依頼します。件数や注文番号を受け渡す場合は、指示でJSONの項目名も指定できます。APIの `GET /tasks/{id}` は `result` にサブタスクごとの `summary` と、得られた場合は `data` を返します。結果がない場合は空配列です。件数が0件だった場合は `data` に `{"count": 0}` を返すよう指定しておくと、結果なしと区別できます。

## MCPクライアントから依頼する

デスクトップエージェントと同じホストで、stdioに対応したMCPクライアントを使います。リポジトリと `uv` が必要です。起動済みのアプリと同じ接続キーをMCPクライアントの環境変数設定に登録します。キーを自動生成している場合は、リポジトリで `docker compose exec -T backend cat /app/data/auth/access-key` を実行して確認できます。

MCPクライアントのサーバー設定に次の値を登録します。

| 項目 | 設定値 |
| --- | --- |
| コマンド | `uv` の絶対パス |
| 引数 | `--directory`, リポジトリの絶対パス, `run`, `--frozen`, `--no-dev`, `--extra`, `mcp`, `python`, `-m`, `ai_desktop_agent.mcp_server` |
| 環境変数 | `AGENT_ACCESS_TOKEN` にアプリの接続キー |

`start_desktop_task` に指示を渡し、返されたタスクIDを `get_desktop_task` に渡します。投入がタイムアウトした場合は、同じ `request_id` と同じ引数で再試行すると、すでに受け付けた作業を重複して開始せずに済みます。実行中の環境への投入はHTTP 409になります。状態が `awaiting_user` の場合は、アプリの操作画面で手動入力を終えて再開します。クライアントはタスクで読み取った内容や操作結果を受け取れるため、信頼できるクライアントに接続キーを登録してください。

## Webhookでタスクの終了を受け取る

1. タスク結果を受け取るHTTP POSTの宛先を用意します。
2. アプリの `.env` に `TASK_WEBHOOK_URL` と32文字以上の `TASK_WEBHOOK_SECRET` を設定し、`./scripts/up.sh` を実行します。URLにはバックエンドから到達できる宛先を指定します。別ホストに送る場合は HTTPS を使います。
3. 受信側で、生のリクエスト本文のHMAC-SHA256を共有シークレットで計算します。`X-Desktop-Agent-Signature` の `sha256=` に続く16進文字列と照合してから本文を処理します。

本文には `event`（`task.finished`）、`event_id`、`task_id`、`vm_id`、`state`（`completed` または `failed`）、`success`、`finished_at`（Unix秒）、`stop_reason`、`result` が入ります。Webhookを有効にしたバックエンドは、操作画面から実行したタスクも送信します。受信側で共有してよい結果を扱ってください。

接続失敗、タイムアウト、HTTP 408・429・5xxでは最大2回再送するため、受信側で `event_id` を使って重複を除いてください。未送信の通知はバックエンド再起動時に失われます。中断したタスクは履歴やAPIで、通知キューの満杯や送信失敗は `docker compose logs backend` で確認できます。
